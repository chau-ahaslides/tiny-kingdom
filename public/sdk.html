aha-room SDK

One small library for scan-to-play rooms: a host-authoritative session, a replicated state document, and a transport you can swap, from today's relay to a plugin inside the presenter and audience apps.

Design draft v0.4 · 11 September 2026 · tiny-kingdom · status: proposal, nothing built yet · v0.2: games no longer name themselves or touch codes; a rooms directory owns codes and reports conflicts · v0.3: worked examples for six game shapes · v0.4: presence built in, roster from the parent when embedded

Why

Seven pages on this site run the same session: a big screen opens a room and shows a QR code, phones scan it, type a name, and start sending input; the big screen owns the game and tells the phones what to show. Each page carries its own copy of that plumbing. The copies have drifted: two of them do not handle a phone that scans before the big screen is up, one never backs off when reconnecting, and every one sanitises names its own way.

PageSessionHow state reaches phones
Survival Quiz, Survival Brawl, Brawl Quizhand-rolled10 Hz snapshots, interpolated on the phone
Gremlin Siegehand-rolled, event stylephase and board messages, per-player quiz messages

Color & Soundhand-rolledJPEG of the sheet, ~1 fps while painting

The session is identical everywhere. The state sync is not, and mostly should not be. The SDK owns the first, offers helpers for the second, and hides the wire behind a transport so the same game can later run inside an AhaSlides presentation without a rewrite.

The model

Three things are true of every room, and the SDK is built around them.

The host is authoritative

One big screen owns the game. Phones send intent, never truth. There is no peer-to-peer and no conflict resolution, because there is nothing to resolve.

Identity, lobby and transport are separate

Who you are, how you get in, and how bytes move are three pieces. Standalone, the SDK does all three. Embedded, the parent app supplies the first two and the third is a bridge.

State is a document; input is a stream

Phase, question, timer, roster and scores live in a small versioned document the host replicates. Anything fast (positions, strokes, pictures) goes through opt-in helpers that a slide never needs.

A game knows nothing about codes

Room codes, join URLs and QR images are the SDK's. A game asks for a room and gets one; if it insists on bringing its own code, the SDK claims it and says clearly when another game already holds it.

Quick start

A game page loads one script and calls one of two entry points. Everything below the line is the SDK's business: the room code, the join URL, the QR, sockets, tokens, reconnects, parsing. The game does not say which game it is; the SDK knows from the page it is running on.

Big screen

import { AhaRoom } from '/js/aha-room.js';

const room = await AhaRoom.host();     // mints a room for this page
room.mountLobby('#card');                 // QR, code, join URL, live count — or render room.code / room.joinUrl / room.qr() yourself

room.on('join',  ({ id, name, rejoin }) => addPainter(id, name));
room.on('leave', ({ id }) => liftBrush(id));
room.on('msg',   (m) => { if (m.t === 'stroke') paint(m.id, m); });

room.state.set({ phase: 'painting', palette, scale: 'Lydian' });   // replicated to every phone
room.state.setFor(id, { streak: 3 });                               // this phone only

Bringing your own code

A game may mint its own code, for a vanity room or because a parent app derived one from a presentation. The SDK claims it with the directory and refuses, loudly, if the code is live for another game or another page.

try {
  room = await AhaRoom.host({ code: 'P8F3K-S12' });
} catch (e) {
  if (e instanceof AhaRoom.RoomConflict) {
    // e.code === 'P8F3K-S12', e.heldBy === '/survival-quiz' (the page that holds it), e.since
    room = await AhaRoom.host();          // fall back to a minted code, or surface the clash
  } else throw e;
}

Reopening a room from the same page is not a conflict: the big screen that reloads gets its room back and phones re-register. A conflict is only ever another page, or another live big screen on the same page, holding that code.

const me = AhaRoom.join({ askName: showNameForm });   // the code comes from the URL the QR opened

Poll: a document and nothing else

No loop, no timer, no privacy. The host writes the question and the counts; phones send a vote. This is most of what a "slide" is.

// big screen
const room = await AhaRoom.host();
room.mountLobby('#card');
const counts = [0, 0, 0], voted = new Set();
room.state.set({ q: 'Which release cadence?', opts: ['Weekly', 'Fortnightly', 'Monthly'], counts, open: true });

room.on('msg', m => {
  if (m.t !== 'vote' || voted.has(m.id) || !room.state.get().open) return;
  const i = m.i | 0; if (i < 0 || i > 2) return;        // phones lie; clamp
  voted.add(m.id); counts[i]++;
  room.state.set({ counts: counts.slice() });                // one patch, coalesced per frame
});
closeBtn.onclick = () => room.state.set({ open: false });

// phone
const me = AhaRoom.join({ askName });
me.on('state', doc => renderPoll(doc.q, doc.opts, doc.counts, doc.open));
optionEl.onclick = i => me.send({ t: 'vote', i });

Late phones get the counts in their welcome snapshot. A phone that reloads has the same id, so it cannot vote twice. Nothing here is a socket.

Quiz: a timer and a private result

The question is public, the correct option is not until the reveal, and each phone gets its own verdict and points. The document carries the deadline as a host timestamp; the phone draws the bar from its host clock.

// big screen
const QUESTIONS = [...];                                   // { q, opts, correct, points }
let n = 0, answers = new Map();
function ask() {
  const Q = QUESTIONS[n];
  answers.clear();
  room.state.set({ phase: 'ask', n, q: Q.q, opts: Q.opts, endsAt: room.now() + 15000, correct: null });
  setTimeout(reveal, 15000);
}
room.on('msg', m => {
  const d = room.state.get();
  if (m.t !== 'answer' || d.phase !== 'ask' || m.n !== d.n || answers.has(m.id)) return;   // stale or repeat
  answers.set(m.id, { i: m.i | 0, at: room.now() });
  room.state.setFor(m.id, { answered: m.i | 0 });           // only this phone: "you picked B"
});
function reveal() {
  const Q = QUESTIONS[n], board = room.state.get().board || {};
  for (const [id, a] of answers) {
    const right = a.i === Q.correct, pts = right ? Q.points : 0;
    board[id] = (board[id] || 0) + pts;
    room.state.setFor(id, { right, pts });                  // the verdict, privately
  }
  room.state.set({ phase: 'reveal', correct: Q.correct, board });   // now everyone may know
  room.report({ kind: 'score', byPlayer: board });          // no-op standalone, results when embedded
}

// phone
me.on('state', (doc, mine) => {
  if (doc.phase === 'ask') showQuestion(doc.q, doc.opts, mine.answered);
  if (doc.phase === 'reveal') showVerdict(doc.correct, mine.right, mine.pts, rank(doc.board, me.id));
});
me.every(100, () => drawBar((me.state.get().endsAt - me.now()) / 15000));   // host time, never a countdown
optionEl.onclick = i => me.send({ t: 'answer', n: me.state.get().n, i });

Because the correct option is written to the document only at reveal time, a broadcast transport with no unicast still keeps the secret: the private slice carries a verdict, not the answer key.

Gremlin Siege: phases, private offers, a board that moves

Three things at different speeds. Phases and the board's guns change a few times a wave: the document. Each phone's quiz offer is its own: a private slice. Enemies march every frame: a stream at 10 Hz, interpolated on the phone.

// big screen
function startWave(w) {
  room.state.set({ phase: 'quiz', wave: w, endsAt: room.now() + 15000, guns, towerHp });
  for (const [id] of room.players) room.state.setFor(id, { offer: pickQuestion(id), streak: streaks.get(id) || 0 });
}
room.on('msg', m => {
  if (m.t === 'answer') {
    const mine = room.state.getFor(m.id);
    if (!mine.offer || m.qid !== mine.offer.qid) return;
    const right = grade(mine.offer, m.i);
    streaks.set(m.id, right ? (streaks.get(m.id) || 0) + 1 : 0);
    room.state.setFor(m.id, { offer: null, right, streak: streaks.get(m.id), canPlace: right ? gunFor(streaks.get(m.id)) : null });
  }
  if (m.t === 'place') {                                  // intent; the host validates the tile
    const mine = room.state.getFor(m.id);
    if (mine.canPlace && freeTile(m.x | 0, m.y | 0)) { guns.push({ by: m.id, kind: mine.canPlace, x: m.x | 0, y: m.y | 0 }); room.state.set({ guns }); room.state.setFor(m.id, { canPlace: null }); }
  }
});
room.stream('enemies', 10, () => enemies.map(e => [e.id, e.x | 0, e.y | 0, e.hp]));   // phones interpolate between these

// phone
me.on('state', (doc, mine) => {
  drawPhases(doc.phase, doc.wave, doc.endsAt - me.now());
  drawGuns(doc.guns, doc.towerHp);
  if (mine.offer) showQuiz(mine.offer); else hideQuiz();
  if (mine.canPlace) showPlacement(mine.canPlace);
});
me.stream('enemies', { interpolate: [1, 2] })            // fields 1 and 2 are x, y
  .on('frame', list => drawEnemies(list));
placeBtn.onclick = () => me.send({ t: 'place', x: tile.x, y: tile.y });

Today this game hand-writes the phase strip countdowns as ticks; with endsAt the strip is right on every phone whatever the latency, and a phone that was asleep snaps to the correct phase on its next message.

Survival Quiz: positions at 10 Hz, taps as intent

The arena moves every frame on the big screen. Phones do not simulate; they show a stream and send where they want their fighter to go.

// big screen
room.on('join', ({ id, name, rejoin }) => { if (!rejoin) spawnFighter(id, name); else fighters.get(id).remote = true; });
room.on('leave', ({ id }) => { const f = fighters.get(id); if (f) f.remote = false; });   // fights on as a bot
room.on('msg', m => {
  if (m.t === 'go') { const f = fighters.get(m.id); if (f && f.remote && !f.dead) f.target = clampToArena(m.x, m.y); }
});
room.state.set({ phase: 'fight', endsAt: room.now() + 60000, roster: [...fighters.values()].map(f => [f.id, f.name, f.kit]) });
room.stream('arena', 10, () => ({
  ps:  [...fighters.values()].map(f => [f.id, f.x | 0, f.y | 0, f.hp | 0, f.face, f.anim, f.dead ? 1 : 0]),
  qs:  quizzes.map(q => [q.x | 0, q.y | 0]),
}));
// a hit is an event, not state: send it once and let phones animate it
function onHit(victim, n, crit) { room.send({ t: 'hit', id: victim, n, crit }); }

// phone
me.on('state', doc => buildArena(doc.roster));
me.stream('arena', { interpolate: { ps: [1, 2] } }).on('frame', s => drawArena(s.ps, s.qs));
me.on('msg', m => { if (m.t === 'hit') popDamage(m.id, m.n, m.crit); });
arena.onpointerdown = e => me.send({ t: 'go', x: e.x | 0, y: e.y | 0 });

This is exactly the message shape the page uses today; the SDK adds the interpolation, the drop-when-behind, and the seat that survives a reload.

Color & Sound: continuous input in, pictures out

Phones are brushes. Every point of a stroke goes up through the input helper, batched; the host paints and plays; the sheet comes back as a picture because no phone could reproduce a watercolour that keeps blooming. Palette and scale are the document.

// big screen
room.state.set({ palette, scale: 'Lydian', ar: W / H });
room.on('msg', m => {
  const p = painter(m.id);
  if (m.t === 'down')  { p.brush = { type: m.b, size: m.z, color: m.c }; down(p, m.x * W, m.y * H, m.pr); }
  if (m.t === 'stroke') for (const [u, v, pr, dt] of m.pts) move(p, u * W, v * H, pr, p.t0 + dt);   // batch carries its own clock
  if (m.t === 'up')    up(p);
});
room.frame(paintCanvas, { long: 640, quality: 0.55, dirty: () => paintedAt > lastFrameAt });

// phone
me.on('state', doc => { setSwatches(doc.palette); fitSheet(doc.ar); });
me.on('frame', img => { if (!myStrokeInFlight) drawSheet(img); });   // hold it while my own stroke is live
const pts = me.input('stroke', { every: 50, quantise: 1e4 });
sheet.onpointerdown = e => { me.send({ t: 'down', b: brush.type, z: brush.size, c: brush.color, x: u(e), y: v(e), pr: e.pressure }); pts.start(); };
sheet.onpointermove = e => pts.push([u(e), v(e), e.pressure]);      // helper adds dt and batches
sheet.onpointerup   = () => { pts.flush(); me.send({ t: 'up' }); };

A phone that joins an hour into the session receives one frame and is current. Undo and Clear on the big screen need no messages: the next frame shows the result.

Solo mode and tests: the memory transport

Every page also works alone. With the memory transport, host and player live in one page and the game runs the same code path it runs in a room. Tests drive both ends without a network.

// page: solo when there is no ?host and no ?join
const room = await AhaRoom.host({ transport: AhaRoom.memory() });
const me   = AhaRoom.join({ transport: room.transport, name: 'You' });   // same page, same game code as a phone
for (let i = 0; i < 5; i++) AhaRoom.join({ transport: room.transport, name: 'Bot ' + i, bot: botBrain });

// test
const room = await AhaRoom.host({ transport: AhaRoom.memory() });
const a = AhaRoom.join({ transport: room.transport, name: 'A' });
room.state.set({ phase: 'ask', n: 0 });
a.send({ t: 'answer', n: 0, i: 1 });
await room.transport.settle();                          // deliver everything queued
assert.equal(room.state.getFor(a.id).answered, 1);
room.transport.drop(a); await room.transport.settle();  // simulate a phone losing signal
assert.equal(room.players.get(a.id).online, false);

The memory transport also answers the question of what a bot is: a player whose brain is a function, joined through the same door as a phone. Survival Quiz's bots and Color & Sound's extra painters become that.

Presence

Who is in the room is a built-in of the session, not something each game reconstructs from join and leave. The big screen shows names arriving as people scan; phones see how many are painting; a quiz waits for enough people. All of that reads from one place.

CallWhat it gives
room.playersThe map above. online flips with join and leave; seat is a small stable index in first-join order, so a game can give each player a consistent colour or avatar without a table of its own; since is host time of first join.
room.on('players', list)The roster as an array, sorted by seat, fired coalesced: a burst of forty scans re-renders a handful of times, not forty. This is what the default lobby card and any custom lobby render from.
room.count(){ total, online }, for the corner of a screen.
doc._players · me.on('players', p)Phones get presence for free. The SDK keeps a reserved slice in the document, { total, online, names }, where names is capped at 40 and sorted by seat. A phone can show "12 painting" or the names arriving without a line of game code. The cap matters: in a room of 500, replicating every name to every phone on every join would be the biggest message stream in the system.
join with rejoinThe big screen can toast "Chau joined" only for genuinely new players and stay quiet when a phone reconnects. The SDK makes the distinction reliable; the game decides what to show.
// big screen: names appear as people scan, a toast for each new one
room.on('players', list => lobbyNames.replaceChildren(...list.map(p => nameChip(p.name, p.seat, p.online))));
room.on('join', ({ name, rejoin }) => { if (!rejoin) toast(name + ' joined'); });
startBtn.disabled = room.count().online < 2;

// phone: "12 painting"
me.on('players', p => tag.textContent = p.online + ' painting');

Presence survives a big-screen reload: the relay keeps the roster and replays it to the new host, so room.players is rebuilt before the game's first frame. That is why a game must render presence from here and never from a counter of its own, which would restart at zero.

State document

The document is a plain JSON object owned by the host. It is meant for what a slide needs: phase, the current question, when the timer ends, the roster, scores. Keep it under 16 KB so any transport carries it in one message.

CallWhat happens
room.state.set(patch)Shallow-merges the patch, bumps the version, broadcasts {t:'patch', v, p}. Deleting a key: set it to null.
room.state.setFor(id, patch)Same for one player's private slice. Delivered only to that player on transports with unicast; on broadcast transports it is tagged and filtered, so treat it as not secret there.
room.state.get() · me.state.get()The current document. On the phone, also me.state.mine().
room.state.getFor(id)One player's private slice as the host last wrote it. The host's own bookkeeping, not a round trip.
me.on('state', fn)Fires with the full document after each applied patch or snapshot. Games render from the document, not from patches.

Consistency rules, which are what make the document survive a slow or lossy transport:

  • Every patch carries the version it produces. A phone that receives version 44 while holding 42 discards it and asks for a snapshot. It never applies out of order.
  • A phone that joins, rejoins, or resyncs gets one full snapshot, then patches. The snapshot is idempotent: applying it twice is harmless.
  • Patches are coalesced: several set calls in one frame go out as one message.
  • The host is the only writer. Phones express intent with send, the host decides, the document changes.

What stays out of the document: anything that changes more than a few times a second. That is what the fast lanes are for.

Time

Timers are the most common thing to get wrong across a network. The SDK keeps a host-clock estimate on every phone and games express deadlines as host timestamps, never as countdown ticks.

room.state.set({ question: q, endsAt: room.now() + 15000 });   // host

me.on('state', doc => {                                            // phone
  const left = Math.max(0, doc.endsAt - me.now());               // me.now() is host time
  drawBar(left / 15000);
});

me.now() is corrected on every snapshot and refined by the round-trip of a ping every few seconds. Accuracy of a few tens of milliseconds is enough for a bar; a phone that was asleep snaps back on its next message. me.every(ms, fn) and room.every(ms, fn) are timers that pause while the page is hidden or the slide is inactive, so a bar never runs while nobody can see it.

Simulation inside the Durable Object, as Marshmallow Live does, is not a helper. It is a different backend with its own room class, and it stays that way.

Reporting embed

A game that runs inside a presentation needs to hand results back: a score per participant, an answer per question, a winner. Standalone, this is a no-op.

room.report({ kind: 'score', byPlayer: { p7: 1200, p9: 800 } });
room.report({ kind: 'answer', player: 'p7', question: 3, choice: 1, correct: true });
room.report({ kind: 'done' });   // the slide can advance

Reports go to the transport, which knows whether there is a parent to tell. The shapes are the only part of the SDK that couples to AhaSlides, so they are kept in one small file.

Wire protocol

Every message is a JSON object with a short t. The SDK reserves types with an underscore; a game's own messages never collide with it.

TypeDirectionFieldsMeaning
_welcomehost → phoneid, name, rejoined, v, doc, mine, nowYou are in. Includes the snapshot so a phone renders after one message.
_join · _leaverelay → hostid, name, rejoinRoster changes. Produced by the transport, not the game.
_snaphost → phonev, doc, mine, nowFull document. Sent on join, on resync, and after any gap.
_patchhost → phonesv, p (and to for a private slice)Shallow merge into the document at version v. Presence travels as an ordinary patch to the reserved _players key, coalesced with whatever else changed that frame.
_resyncphone → hostvI hold version v and saw a gap; send a snapshot.
_ping · _pongbotht0, nowClock offset and liveness.
_nohost · _hostgonerelay → phone—The big screen is not here yet, or left.
_frame · _stream · _inputvarieshelper-specificFast lanes.
anything elseeithergame-definedDelivered as 'msg'. Phone messages get id stamped by the transport.
Limits. One message under 64 KB; the document under 16 KB; a phone sends at most 20 messages a second (the input helper enforces this by batching); the host sends the document at most once per animation frame. Frames are the exception and are governed by their own throttle: 0.7 s plus 30 ms per phone, capped at 2.5 s.

Rooms and codes

Today each page mints a four-character code at random, the relay names its Durable Object by that code alone, and the worker carries one hand-written redirect per game (/sq/, /tr/, /cs/…). Three things go wrong with that as games multiply: two rooms can draw the same code and silently share a relay, even across games; a page can register a prefix another page already uses and nobody finds out until a phone 404s; and every page has to know its own prefix, which is exactly the kind of thing a game should not know.

v0.2 replaces all of it with a small rooms directory, a single Durable Object in the worker, and one join route.

EndpointBodyResponse
POST /api/room{ page: '/color-and-sound' }201 { code, joinUrl }: a fresh code, checked against every live room before it is handed out.
POST /api/room{ page, code: 'P8F3K-S12' }201 if free, or held by this page with no live big screen; 409 { conflict: { code, heldBy, since } } if another page, or a live big screen on this page, holds it. The SDK turns the 409 into RoomConflict.
GET /j/CODE—302 to the page that opened the room, with ?join=CODE; 404 page saying the room has ended if the code is unknown or expired.
/ws/CODE—Unchanged for phones and hosts; the worker resolves the code through the directory and names the relay page + ':' + code, so a stale code from another game can never reach the wrong room.

The directory keeps { code → page, createdAt, lastSeen, hostLive }, hears a heartbeat from each live host, and expires rooms after a few idle hours, so codes recycle and the four-character space stays roomy. Codes are 4 to 32 characters from a confusable-free alphabet (no 0 O 1 I L), so vanity and presentation-derived codes fit the same route. The old per-game prefixes stay as aliases for QR codes already printed.

What this buys: a game is identified by its page path, a room by a code the directory guarantees unique, the join URL is the only thing a phone needs, and adding a game to the site adds nothing to the worker.

Transports

A transport moves bytes and knows who is on the other end. It is the only place a socket, a room code, or a parent window is ever touched. The game never sees it.

interface Transport {
  caps: { unicast: boolean; providesIdentity: boolean; providesRoom: boolean; providesRoster: boolean;
          maxBytes: number; maxRate: number; fastLanes: boolean };
  connect(role: 'host' | 'player', opts: { room?: string; identity?: { id, name, token } }): Promise<void>;
  send(obj: object, to?: string): void;
  close(): void;
  onMessage(fn: (obj: object) => void): void;          // player messages arrive with id stamped
  onPeer(fn: (ev: 'join' | 'leave', peer: { id, name, rejoin }) => void): void;
  onStatus(fn: (s: string) => void): void;
}

The SDK reads caps and adapts: no lobby UI when the transport provides identity and a room; setFor tagged rather than private when there is no unicast; fast-lane helpers refuse to start when fastLanes is false, so a game finds out at development time, not in a room.

Embedding in the presenter and audience apps

The audience app already mounts a game per active slide and remounts on slide change; the presenter app already knows every participant's id and name. Embedding a room game means giving both apps an iframe and telling the SDK what it no longer has to do. Two steps, in this order.

Step 1 · Hybrid: identity from the parent, data over the relay

The presenter app embeds the big-screen page; the audience app embeds the phone page. The presenter app derives a code from the presentation and slide and passes it down; the SDK on the big screen claims it through the directory, exactly as a game bringing its own code would, so a clash with another game is reported rather than silently shared. There is no QR to show. Bytes still flow directly between the iframes and the relay: nothing crosses the AhaSlides channel, the game is unchanged, and the only new part is report().

presenter app, big screen
<iframe src="https://tiny-kingdom…/color-and-sound?host=1&embed=1&room=P8F3K-S12">

audience app, phone
<iframe src="https://tiny-kingdom…/color-and-sound?join=P8F3K-S12&embed=1&name=Chau&token=a91…">

The game code sees none of this: the embed transport reads room, name and token from the URL (or from a postMessage, for tokens that should not appear in a URL) and reports providesRoom and providesIdentity, so mountLobby renders nothing and askName is never called. The token is the participant id, so a participant who reloads or switches tabs keeps their seat, exactly as today.

The audience is already there

Inside a presentation, people joined before the game loaded, and the lobby lives in the parent app. Two things follow.

  • The host arrives after the players. Phone iframes may reach the relay before the presenter's iframe exists. The relay already handles this: phones wait, and when the host connects it receives a join for everyone present. The game sees the same events in the same order as a standalone room.
  • The roster comes from the parent, not from connections. A quiz slide wants to show "24 in the room" the moment it loads, including people who have not opened the slide yet, and a leaderboard wants names for participants who never sent a message. The parent posts the roster on load and on every change; the transport reports providesRoster; room.players is populated before any phone connects, with online telling the game who has actually opened the slide. So room.count() reads { total: 24, online: 18 } while people are still arriving, and the game can wait for a threshold or start regardless. join and leave keep meaning connected and disconnected, so a game written against the standalone relay behaves the same.

The two paths must agree on identity: the id the parent lists in the roster is the id it gives that participant's iframe, and that id is the reconnect token. A phone that connects later lands on its existing seat rather than a new one.

Whether the presenter app persists those reports as presentation results or only as a leaderboard is a product decision, not an SDK one.

Step 2 · Bridge: the parent carries the messages later

Same SDK interface, new transport: the iframe hands each message to the parent over postMessage and the parent forwards it over the presentation's realtime channel. Worth doing when the product wants no second backend. Three constraints, all of which the design above already absorbs:

  • Broadcast, not unicast. Private slices are tagged and filtered on the phone. Fine for state, not for a correct answer before its reveal. Games that need secrecy keep it on the host until reveal time, which is good practice on any transport.
  • Rate. Thirty phones sending strokes at 15 messages a second is not a load that channel should take. The bridge caps rate and message size in caps; fast lanes refuse to start and stay on the relay if the game needs them.
  • Ordering and loss. Not guaranteed. This is exactly why the document is versioned and resyncs from a snapshot.

Rules for game authors

The one rule that keeps the swap possible: a game never touches a socket, a room code, a join URL, a QR, localStorage, or window.parent. It talks to room and me, and nothing else. The only code a game may ever hold is one it chose to bring, and then the SDK tells it whether it got it. Everything the SDK cannot do through that surface is a gap in the SDK, to be fixed there.
  • Render from the document, not from the sequence of patches. A phone may skip patches and land on a snapshot.
  • Deadlines are host timestamps. Never ship a countdown.
  • Phones send intent (answer, move, stroke), the host decides and writes the document. If a phone could break the game by lying, the host is trusting it too much.
  • Anything a phone must not know yet stays on the host. Reveal by writing it into the document.
  • Sanitise nothing yourself. Names arrive clean, ids are stamped by the transport, numbers are still numbers and must be clamped by the game as today.
  • Design for a phone that reloads mid-game. With a reserved seat and a snapshot on rejoin, that should be invisible.
  • Render presence from room.players or the _players slice, never from a counter of your own. Do not treat "no join yet" as "no players": when embedded, the roster is full before anyone connects.

Open questions

  • Where do reports land? Presentation results, a leaderboard, or both. Decides the report shapes in phase 1.
  • Guessable embed codes. A code derived from presentationId-slideId lets both apps agree without talking, but anyone who knows the ids can join. If that matters, the presenter app mints a random code and passes it down; the directory does not care which.
  • Who owns the big screen when the presenter's tab reloads? Today the relay replaces the host and phones re-register. Inside a presentation, the new host should also receive a snapshot of its own document, which means the host persists it (localStorage, per room) or the directory keeps the last snapshot next to the room record. The second is cleaner and small.
  • Two big screens on purpose. A rehearsal and a live show on the same page would want different rooms, which minted codes give for free; a brought code is refused for the second screen. Is that the right default, or should a page be able to hand a room over explicitly?
  • Package form. One ES module on this site is enough for phase 1. Publishing to the org registry only matters when the audience app imports it directly rather than embedding a page.
