aha-room SDK

One small library for scan-to-play rooms: a host-authoritative session, a replicated state document, and a transport you can swap, from today's relay to a plugin inside the presenter and audience apps.

Design draft v0.1 · 11 September 2026 · tiny-kingdom · status: proposal, nothing built yet

Why

Seven pages on this site run the same session: a big screen opens a room and shows a QR code, phones scan it, type a name, and start sending input; the big screen owns the game and tells the phones what to show. Each page carries its own copy of that plumbing. The copies have drifted: two of them do not handle a phone that scans before the big screen is up, one never backs off when reconnecting, and every one sanitises names its own way.

PageSessionHow state reaches phones
Survival Quiz, Survival Brawl, Brawl Quizhand-rolled10 Hz snapshots, interpolated on the phone
Gremlin Siegehand-rolled, event stylephase and board messages, per-player quiz messages
Marshmallow, Marshmallow Livehand-rolledphysics simulated in the Durable Object
Color & Soundhand-rolledJPEG of the sheet, ~1 fps while painting

The session is identical everywhere. The state sync is not, and mostly should not be. The SDK owns the first, offers helpers for the second, and hides the wire behind a transport so the same game can later run inside an AhaSlides presentation without a rewrite.

The model

Three things are true of every room, and the SDK is built around them.

The host is authoritative

One big screen owns the game. Phones send intent, never truth. There is no peer-to-peer and no conflict resolution, because there is nothing to resolve.

Identity, lobby and transport are separate

Who you are, how you get in, and how bytes move are three pieces. Standalone, the SDK does all three. Embedded, the parent app supplies the first two and the third is a bridge.

State is a document; input is a stream

Phase, question, timer, roster and scores live in a small versioned document the host replicates. Anything fast (positions, strokes, pictures) goes through opt-in helpers that a slide never needs.

Quick start

A game page loads one script and calls one of two entry points. Everything below the line is the SDK's business: the room code, the QR, sockets, tokens, reconnects, parsing.

Big screen

import { AhaRoom } from '/js/aha-room.js';

const room = await AhaRoom.host({ game: 'cs', lobby: { qr: '#qrimg', code: '#code', url: '#joinurl' } });

room.on('join',  ({ id, name, rejoin }) => addPainter(id, name));
room.on('leave', ({ id }) => liftBrush(id));
room.on('msg',   (m) => { if (m.t === 'stroke') paint(m.id, m); });

room.state.set({ phase: 'painting', palette, scale: 'Lydian' });   // replicated to every phone
room.state.setFor(id, { streak: 3 });                               // this phone only

Phone

const me = AhaRoom.join({ game: 'cs', askName: showNameForm });   // code comes from the URL

me.on('welcome', ({ id, name, rejoined }) => showSheet());
me.on('state',   (doc, mine) => render(doc.phase, doc.palette, mine.streak));
me.on('status',  (s) => setTag(s));   // 'waiting-for-host' | 'reconnecting' | 'host-left' | 'ok'

me.input('stroke', { every: 50 })   // batches points into one message per 50 ms
  .push([u, v, pressure, dt]);

State document

The document is a plain JSON object owned by the host. It is meant for what a slide needs: phase, the current question, when the timer ends, the roster, scores. Keep it under 16 KB so any transport carries it in one message.

CallWhat happens
room.state.set(patch)Shallow-merges the patch, bumps the version, broadcasts {t:'patch', v, p}. Deleting a key: set it to null.
room.state.setFor(id, patch)Same for one player's private slice. Delivered only to that player on transports with unicast; on broadcast transports it is tagged and filtered, so treat it as not secret there.
room.state.get() · me.state.get()The current document. On the phone, also me.state.mine().
me.on('state', fn)Fires with the full document after each applied patch or snapshot. Games render from the document, not from patches.

Consistency rules, which are what make the document survive a slow or lossy transport:

  • Every patch carries the version it produces. A phone that receives version 44 while holding 42 discards it and asks for a snapshot. It never applies out of order.
  • A phone that joins, rejoins, or resyncs gets one full snapshot, then patches. The snapshot is idempotent: applying it twice is harmless.
  • Patches are coalesced: several set calls in one frame go out as one message.
  • The host is the only writer. Phones express intent with send, the host decides, the document changes.

What stays out of the document: anything that changes more than a few times a second. That is what the fast lanes are for.

Time

Timers are the most common thing to get wrong across a network. The SDK keeps a host-clock estimate on every phone and games express deadlines as host timestamps, never as countdown ticks.

room.state.set({ question: q, endsAt: room.now() + 15000 });   // host

me.on('state', doc => {                                            // phone
  const left = Math.max(0, doc.endsAt - me.now());               // me.now() is host time
  drawBar(left / 15000);
});

me.now() is corrected on every snapshot and refined by the round-trip of a ping every few seconds. Accuracy of a few tens of milliseconds is enough for a bar; a phone that was asleep snaps back on its next message.

Fast lanes opt-in

Three helpers, each a copy of a pattern that already works on this site. None of them is loaded unless the game asks.

HelperPattern it packagesFrom
room.stream(name, hz, fn) · me.stream(name, opts)Fixed-rate snapshots of arrays of numbers. The phone side keeps the last two and interpolates, so 10 Hz looks like 60. Rounds numbers, drops frames when the socket is behind.Survival Quiz
room.frame(canvas, opts) · me.on('frame', img)A JPEG of a canvas, only when the game marks it dirty, throttled by player count. The latest frame is cached and sent to whoever joins, so nothing is ever replayed.Color & Sound
me.input(name, opts)Quantises and batches high-rate input (touch points, taps) into one message per interval, with a millisecond offset per sample so the host can recover timing.Color & Sound

Simulation inside the Durable Object, as Marshmallow Live does, is not a helper. It is a different backend with its own room class, and it stays that way.

Reporting embed

A game that runs inside a presentation needs to hand results back: a score per participant, an answer per question, a winner. Standalone, this is a no-op.

room.report({ kind: 'score', byPlayer: { p7: 1200, p9: 800 } });
room.report({ kind: 'answer', player: 'p7', question: 3, choice: 1, correct: true });
room.report({ kind: 'done' });   // the slide can advance

Reports go to the transport, which knows whether there is a parent to tell. The shapes are the only part of the SDK that couples to AhaSlides, so they are kept in one small file.

Wire protocol

Every message is a JSON object with a short t. The SDK reserves types with an underscore; a game's own messages never collide with it.

TypeDirectionFieldsMeaning

_join · _leaverelay → hostid, name, rejoinRoster changes. Produced by the transport, not the game.
_snaphost → phonev, doc, mine, nowFull document. Sent on join, on resync, and after any gap.
_patchhost → phonesv, p (and to for a private slice)Shallow merge into the document at version v.
_resyncphone → hostvI hold version v and saw a gap; send a snapshot.
_ping · _pongbotht0, nowClock offset and liveness.
_nohost · _hostgonerelay → phone—The big screen is not here yet, or left.

anything elseeithergame-definedDelivered as 'msg'. Phone messages get id stamped by the transport.
Limits. One message under 64 KB; the document under 16 KB; a phone sends at most 20 messages a second (the input helper enforces this by batching); the host sends the document at most once per animation frame. Frames are the exception and are governed by their own throttle: 0.7 s plus 30 ms per phone, capped at 2.5 s.

Transports

A transport moves bytes and knows who is on the other end. It is the only place a socket, a room code, or a parent window is ever touched. The game never sees it.

interface Transport {
  caps: { unicast: boolean; providesIdentity: boolean; providesRoom: boolean;
          maxBytes: number; maxRate: number; fastLanes: boolean };
  connect(role: 'host' | 'player', opts: { room?: string; identity?: { id, name, token } }): Promise<void>;
  send(obj: object, to?: string): void;
  close(): void;
  onMessage(fn: (obj: object) => void): void;          // player messages arrive with id stamped
  onPeer(fn: (ev: 'join' | 'leave', peer: { id, name, rejoin }) => void): void;
  onStatus(fn: (s: string) => void): void;
}

The SDK reads caps and adapts: no lobby UI when the transport provides identity and a room; setFor tagged rather than private when there is no unicast; fast-lane helpers refuse to start when fastLanes is false, so a game finds out at development time, not in a room.

Embedding in the presenter and audience apps

The audience app already mounts a game per active slide and remounts on slide change; the presenter app already knows every participant's id and name. Embedding a room game means giving both apps an iframe and telling the SDK what it no longer has to do. Two steps, in this order.

Step 1 · Hybrid: identity from the parent, data over the relay

The presenter app embeds the big-screen page; the audience app embeds the phone page. Both derive the room from the presentation and slide, so there is no code to exchange and no QR to show. Bytes still flow directly between the iframes and the relay: nothing crosses the AhaSlides channel, the game is unchanged, and the only new part is report().

presenter app, big screen
<iframe src="https://tiny-kingdom…/color-and-sound?host=1&embed=1&room=P8f3k-s12">

audience app, phone
<iframe src="https://tiny-kingdom…/color-and-sound?join=P8f3k-s12&embed=1&name=Chau&token=a91…">

The relay names rooms by string, so presentationId-slideId is a valid room. The worker's join route gains a second form for these longer names. The token is the participant id, so a participant who reloads or switches tabs keeps their seat, exactly as today.

The audience app's skin engine drives its own quiz loop and leaderboard. A room game does not join that loop: it is its own slide type, with its own results, which is why report exists. Whether the presenter app persists those reports as presentation results or only as a leaderboard is a product decision, not an SDK one.

Step 2 · Bridge: the parent carries the messages later

Same SDK interface, new transport: the iframe hands each message to the parent over postMessage and the parent forwards it over the presentation's realtime channel. Worth doing when the product wants no second backend. Three constraints, all of which the design above already absorbs:

  • Broadcast, not unicast. Private slices are tagged and filtered on the phone. Fine for state, not for a correct answer before its reveal. Games that need secrecy keep it on the host until reveal time, which is good practice on any transport.
  • Rate. Thirty phones sending strokes at 15 messages a second is not a load that channel should take. The bridge caps rate and message size in caps; fast lanes refuse to start and stay on the relay if the game needs them.
  • Ordering and loss. Not guaranteed. This is exactly why the document is versioned and resyncs from a snapshot.

Rules for game authors

The one rule that keeps the swap possible: a game never touches a socket, a room code, localStorage, or window.parent. It talks to room and me, and nothing else. Everything the SDK cannot do through that surface is a gap in the SDK, to be fixed there.
  • Render from the document, not from the sequence of patches. A phone may skip patches and land on a snapshot.
  • Deadlines are host timestamps. Never ship a countdown.
  • Phones send intent (answer, move, stroke), the host decides and writes the document. If a phone could break the game by lying, the host is trusting it too much.
  • Anything a phone must not know yet stays on the host. Reveal by writing it into the document.
  • Sanitise nothing yourself. Names arrive clean, ids are stamped by the transport, numbers are still numbers and must be clamped by the game as today.
  • Design for a phone that reloads mid-game. With a reserved seat and a snapshot on rejoin, that should be invisible.

Migration

Nothing forces the pages to move together: the relay does not change, so a migrated page and an unmigrated one coexist. Suggested order, easiest and most instructive first.

Roadmap

  1. Phase 1 — core. aha-room.js: session, state document, time, reporting stub; relay, memory and embed transports; the longer room-name route in the worker. Move Color & Sound and Gremlin Siege. About 250 lines of SDK and one page of docs.
  2. Phase 2 — fast lanes. stream, frame, input. Move the other four pages and delete the copies.
  3. Phase 3 — bridge. When the presenter app has a plugin host, the bridge transport and the report shapes it expects. No game changes.

Open questions

  • Where do reports land? Presentation results, a leaderboard, or both. Decides the report shapes in phase 1.
  • Room naming for embeds. presentationId-slideId is derivable by both apps but guessable. If rooms need to be unguessable, the presenter app mints them and passes them down.
  • Who owns the big screen when the presenter's tab reloads? Today the relay replaces the host and phones re-register. Inside a presentation, the new host should also receive a snapshot of its own document, which means the host persists it (localStorage, per room) or the relay keeps the last snapshot. The second is cleaner and small.
  • Package form. One ES module on this site is enough for phase 1. Publishing to the org registry only matters when the audience app imports it directly rather than embedding a page.
